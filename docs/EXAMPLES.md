# 작업 종류별 적용

## 간단한 UI 수정

기존 버튼의 문구와 레이아웃만 수정한다면 관련 컴포넌트·스타일을 읽고 변경합니다.
DOM/컴포넌트 테스트가 문구를 검증하고, 화면 배치가 핵심이면 브라우저로 결과를 봅니다.
계약서, 새 디자인 시스템, DB integration, 다중 에이전트는 필요하지 않습니다.
브라우저를 실행하지 못했다면 시각 검증까지 완료했다고 보고하지 않습니다.

## 두 서비스의 read 연동

격리 환경의 provider 데이터 한 건을 consumer의 실제 HTTP adapter로 읽어
사용자에게 필요한 결과까지 연결합니다. 실제로 배포할 이미지·proxy·인증 경로를 포함하는지 구분합니다.
두 revision, scenario, 첫 실패 단계, 최종 결과를 기존 테스트 보고서에 남깁니다.
소비자 테스트가 provider 전체를 mock하면 양자 호환성 증거는 아닙니다.
통과한 경로로 기반을 재사용하되 write의 부작용까지 입증됐다고 추론하지 않습니다.

## 결제/재고 write

정상 요청, 중복·동시 요청, 응답 유실 뒤 재조회/재시도, 권한 거부를 검증합니다.
멱등키, durable 상태, 외부 서비스의 sandbox를 사용합니다. 불확실한 요청을 무작정 재전송하지 않습니다.
독립 리뷰와 승인된 실제 효과가 필요하지만 읽기 조사·로컬 구현까지 멈출 필요는 없습니다.

## ML/OCR 학습

스키마·전처리·데이터 경로·gradient/배치 전달은 빠른 결정적 테스트로 확인합니다.
작은 배치로 실제 학습/추론이 도는지 먼저 검증하고, 고정된 held-out set과 seed/환경을 기록합니다.
평균 지표뿐 아니라 실패 유형·분포·분할 누출을 확인합니다. unit 통과를 모델 품질로 바꾸지 않습니다.
초기 파이프라인 확인을 위해 전체 학습을 반복하거나 학습 전에 범용 실험 플랫폼을 만들지 않습니다.
GPU/유료 API/장시간 작업은 승인된 예산을 넘지 않습니다.

## 모바일·장치·인프라

시뮬레이터 통과와 실제 기기 통과를 구별합니다. build/config 문법 검사와 배포 이미지를 부팅한 검증도 다릅니다.
목표 환경을 사용할 수 없으면 가용한 검증을 하고 실제 환경 검증만 남겨둡니다.
권한이 없다는 이유로 보안 검증을 끄거나 다른 도구로 우회하지 않습니다.
